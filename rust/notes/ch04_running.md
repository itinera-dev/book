In Rust, `LocalExecutor::run` returns `Result<JourneyResult, Refusal>`. The `Err` side is only for a refusal: a journey that failed or was aborted is still `Ok`, and `result.status` says how it ended. Most mistakes in how a workflow is put together never reach `run` at all, because the macros refuse them at compile time. `run` takes the executor as `&mut self`, so the compiler itself prevents two journeys from running on one executor at the same time. A panic is not a failure of the model: it is never caught, and it reaches whoever called `run`.

The asynchronous form needs the `async` feature. Its steps and hooks are `async fn`, the workflow is declared `asynchronous`, its reporter implements `AsyncReporter` and is listed under `async_reporters`, and the role's trait is `Sync`, since an asynchronous hook may move between threads while it holds the role. It runs on `AsyncLocalExecutor`, whose `run` returns a future; here `futures::executor::block_on` waits for it. A synchronous step in an asynchronous workflow, or the reverse, does not compile.
